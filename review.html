02P0 核心

Java 语言与对象模型

把“会写 Java”升级为“能解释类型、对象、相等性、不可变性和运行时行为”。

10 分钟速读

必须闭卷讲清的八件事

只有值传递

基本类型传值本身，对象参数传引用值的副本。方法能改对象状态，不能替换调用方变量。

相等性契约

== 比较基本值或引用身份，equals 表达逻辑相等。重写 equals 时必须同步重写 hashCode。

不可变对象

状态构造后不变，字段通常 final，不暴露可变内部对象。利于线程安全、缓存和 Map 键稳定。

String

不可变，字符串常量池复用字面量。频繁拼接用 StringBuilder，跨线程共享拼接才考虑 StringBuffer。

重载与重写

重载在编译期按参数签名选择，重写在运行期按实际类型动态分派。静态、私有方法不参与普通动态分派。

抽象边界

接口表达能力契约，抽象类承载共享状态与模板。优先组合以降低继承耦合。

final

修饰变量表示只赋值一次，修饰方法禁止重写，修饰类禁止继承。引用 final 不代表对象内部不可变。

装箱陷阱

包装类型可为 null，拆箱可能 NPE；Integer 小值缓存不能作为相等性依据，比较数值用 equals 或拆箱。

对象创建与初始化顺序

首次主动使用类时触发加载、验证、准备、解析和初始化。创建对象时先分配并清零实例内存，再设置对象头，随后按继承关系执行父类与子类的实例初始化和构造器。面试中要区分“类初始化”和“对象初始化”，也不要把 HotSpot 的具体布局当成 Java 语言规范承诺。

equals 与 hashCode 为什么绑定

哈希容器先用 hash 缩小桶范围，再在候选元素中做相等性判断。如果两个逻辑相等对象产生不同 hash，它们可能进入不同桶，导致查找失败。契约要求 equals 相等时 hashCode 必须相等，反向不要求。

public final class UserId {
    private final long value;

    @Override
    public boolean equals(Object other) {
        return this == other
            || other instanceof UserId
            && value == ((UserId) other).value;
    }

    @Override
    public int hashCode() {
        return Long.hashCode(value);
    }
}

深拷贝、浅拷贝与防御性复制

浅拷贝只复制当前对象字段，字段中的可变引用仍共享；深拷贝递归复制对象图，但成本高且语义容易含糊。工程上更常见的做法是定义不可变值对象，在构造和 getter 边界做防御性复制，并明确所有权，而不是到处调用 clone。

继承

表达 is-a，能复用受保护实现，但父类变化会向下传播。适合稳定模板，不适合仅为复用几行代码。

组合

表达 has-a，通过委托复用能力，依赖可替换、测试更容易。默认优先选择。

接口

定义对外能力，可多实现。Java 8 默认方法用于接口演进，但不要把接口变成状态容器。

易错点与工程边界

  • 不要说“对象按引用传递”。Java 传递的是引用值的副本。
  • 不可变不等于所有字段必须是基本类型，关键是外部无法观察到状态变化。
  • final 提供初始化安全性相关语义，但不能自动让整个对象线程安全。
  • 枚举适合有限常量及其行为，不适合承载频繁变化的数据库配置。
  • 反序列化、反射或 Unsafe 可能绕过普通构造路径，框架场景要单独分析。

深入原理

HashMap 主链路

计算扰动 hash→(n - 1) & hash 定位→空桶直接插入→同键覆盖→链表或树追加→超过阈值扩容

容量为什么是 2 的幂

当数组长度是 2 的幂时，取模可以转化为位与。Java 8 扩容为两倍后，节点只需判断旧容量对应的那一位：为 0 留在原索引，为 1 移动到原索引加旧容量。这样无需重新做完整取模，也能保持链内相对顺序。默认负载因子 0.75 是空间与冲突概率的折中，不是所有场景的最佳值。

树化不是达到 8 就一定发生

Java 8 中桶内节点达到树化阈值时，还要看表容量是否足够。容量较小时优先扩容，因为分散元素通常比维护红黑树更划算。具体阈值属于实现细节，回答时既要知道常见实现，也要标明版本边界。

异常设计与资源关闭

受检异常

调用方被强制处理或声明，适合明确可恢复、需要决策的失败。滥用会造成层层 throws 和无意义包装。

运行时异常

适合编程错误、前置条件破坏或统一业务异常体系。不是“不需要处理”，而是由合适边界统一转换。

try-with-resources

按声明逆序关闭 AutoCloseable 资源。主体异常优先，关闭异常进入 suppressed，排障时不要忽略。

扩展与 IO

反射、SPI 与 NIO

反射和 SPI 解决不同问题

反射让程序在运行时查看类型、构造对象和调用成员；SPI 通过约定的服务描述发现实现，常用于驱动、日志或插件。SPI 涉及类加载器可见性，容器中常借助线程上下文类加载器跨越父加载器无法看见子路径实现的问题。

传统阻塞 IO连接通常绑定处理线程简单，连接多时线程成本高
NIOChannel + Buffer + Selector少量线程管理大量就绪连接
异步 IO提交后由完成事件通知平台实现与回调模型需要分析

易错点与工程边界

  • LinkedList 单次节点插入是 O(1)，但找到位置仍可能是 O(n)，业务中通常不因“插入多”就选它。
  • Collections.synchronizedMap 只包装单次操作，迭代和复合逻辑仍需要外部同步。
  • ConcurrentHashMap 不允许 null，避免并发下无法区分“不存在”和“值为 null”。
  • Stream 强调声明式数据处理，不自动更快。并行流使用公共线程池，服务端需要谨慎。
  • 捕获 Exception 后只打印消息会丢失堆栈与上下文，转换异常必须保留 cause。

深入原理

Java 8：Stream 不是循环的语法糖

惰性流水线与终止操作

中间操作描述转换，通常在终止操作到来后才开始拉取数据。无状态操作如 map、filter 易于流水；sorted、distinct 等有状态操作可能需要缓存。Stream 默认只消费一次，不应在操作中修改外部共享状态。并行流是否获益取决于数据规模、拆分成本、计算强度和公共线程池竞争。

Optional 的正确边界

适合表达方法可能没有返回值，不宜普遍作为实体字段、方法参数或集合元素。不要用 isPresent + get 重写 if，优先使用 map、flatMap、orElseGet 等组合操作。

return repository.findById(id)
    .filter(User::isActive)
    .map(UserView::from)
    .orElseThrow(UserNotFound::new);

record 是浅不可变，不是深不可变

record 组件引用不能重新指向，但组件引用的 List 等对象仍可被修改。若领域要求真正不可变，应在紧凑构造器中 List.copyOf，并避免泄漏可变对象。record 适合值语义，不适合依赖可变身份与代理增强的实体。

适合大量阻塞型并发，不负责让 CPU 计算变快

虚拟线程让“一个请求一个线程”的同步代码在大量等待场景下更可扩展。它提升的是吞吐与可并发等待数量，不会缩短 CPU 密集任务。不要把虚拟线程池化来限制并发，应使用信号量等机制保护数据库连接、下游配额等稀缺资源。

Java 21 的版本边界

在 Java 21 中，虚拟线程在某些 synchronized 块内执行阻塞操作或执行 native / foreign 调用时可能发生 pinning，载体线程不能及时释放。应通过 JFR、线程转储和压测发现，而不是因此全面禁用 synchronized。后续 JDK 对该行为有改进，面试回答必须说明所讨论的版本。

  • 升级 JDK 不能只看编译通过，还要验证 GC、反射、模块封装、代理、监控和第三方依赖。

JVM、GC 与内存排障

10 分钟速读

JVM 主干知识

运行时区域

堆存对象，线程栈存栈帧，本地方法栈服务 native，程序计数器记录执行位置，元空间存类元数据。

对象分配

通常先在线程本地分配缓冲区或 Eden 分配，大对象、分配失败和收集器策略会改变路径。

可达性分析

从 GC Roots 向下搜索，无法到达的对象才有资格回收。引用计数不能可靠处理循环引用。

分代假设

多数对象朝生夕灭，少数长期存活。年轻代高频回收，晋升后由老年代机制处理。

类加载

加载、链接、初始化。双亲委派降低类型重复和核心类被替换风险，但 SPI、容器、热部署有特殊需求。

排障原则

先保现场与业务，再用指标缩小范围，最后通过线程栈、GC 日志、堆转储或事件记录证明。

深入原理

Happens-before 是可见性的推理规则

程序次序解锁 → 后续加锁volatile 写 → 后续读start 前 → 新线程动作线程动作 → join 返回传递性

volatile 为什么不能保证 i++

i++ 包含读取、计算、写回三个动作。volatile 能让线程看到较新的值，也禁止部分重排序，但两个线程仍可能读取同一个旧值后分别写回。需要 synchronized、Lock、AtomicInteger 或把状态所有权收拢到单线程。

双重检查为什么要 volatile

对象创建可抽象为分配内存、初始化、发布引用。若允许重排序，另一个线程可能看到非空引用却观察到未完成初始化。volatile 发布与读取建立必要的可见性和顺序约束。

private static volatile Client instance;

static Client getInstance() {
    if (instance == null) {
        synchronized (Client.class) {
            if (instance == null) {
                instance = new Client();
            }
        }
    }
    return instance;
}
AQS

独占锁的一次竞争

尝试 CAS 改 state失败入同步队列检查前驱安全挂起前驱释放被唤醒后重试成功成为持有者

公平与非公平

公平锁在尝试获取前检查是否有排队前驱，减少插队但增加调度与切换成本。非公平锁允许刚到的线程直接竞争，通常吞吐更高但等待方可能更久。ReentrantLock 还提供可中断、超时获取和多个 Condition，选择它不是因为 synchronized “低级”。

线程池

容量要从资源与过载反推

任务到达核心线程未满新建核心线程否则进入工作队列队列满扩到最大线程仍满拒绝策略
CPU 密集近似：线程数 ≈ CPU 核数 + 1 I/O 密集初估：线程数 ≈ 核数 × (1 + 等待时间 / 计算时间)

公式只用于起点。最终值由压测中的吞吐、P99、CPU、队列等待、连接池和下游容量决定。

有界队列是一种背压

无界队列让最大线程数失去扩容意义，并把过载隐藏成越来越长的等待与内存占用。有界队列配合明确拒绝策略，能更早暴露容量上限。CallerRunsPolicy 可让提交方减速，但如果提交方是关键网络线程，也可能扩大故障，必须结合线程角色分析。

按协调问题选择

易错点与工程边界

  • ConcurrentHashMap 的线程安全只覆盖它提供的单次或原子复合 API，先 get 再 put 仍可能竞态。
  • 锁的范围应覆盖不变量，不是越小越好。拆得过小可能破坏跨字段一致性。
  • 在线程池任务中吞掉 InterruptedException 会破坏取消协议，通常应恢复中断标记或向上转换。
  • CompletableFuture 默认异步方法可能使用公共 ForkJoinPool，服务端应明确执行器和容量。

一条查询怎样使用索引

根节点：键范围与子页指针
中间页 A中间页 B中间页 C
叶子页 1 ⇄叶子页 2 ⇄叶子页 3

二级索引叶子：索引列 + 主键；聚簇索引叶子：完整行记录。

最左前缀是排序能力的结果

联合索引 (a, b, c) 先按 a 排，再在相同 a 内按 b 排，最后按 c 排。因此跳过 a 时，全局的 b 并不连续有序。范围条件后的列是否还能用于过滤、排序或索引下推，要结合具体条件和优化器执行计划，不能用一句“范围后全部失效”概括。

覆盖索引减少回表

若查询所需列都能从二级索引取得，无需再按主键访问聚簇索引。索引不是越宽越好，宽索引会增加空间、写放大和缓存压力，应以高频关键查询收益为依据。

WHERE user_id = ?

ORDER BY created_at DESC
LIMIT 20;

INDEX idx_user_time_status_amount
  (user_id, created_at, status, amount)

持久化

一次提交的日志协作

修改缓冲页与 undo→写 redo prepare→写 binlog→redo commit→按策略刷盘

两阶段提交解决日志一致性

redo log 属于 InnoDB，binlog 属于 Server 层。若二者独立提交，崩溃可能导致存储状态与复制日志不一致。两阶段提交通过 prepare 与 commit 状态协调恢复判断。具体持久性还受 innodb_flush_log_at_trx_commit、sync_binlog 和硬件缓存影响。

复制与拆分

副本不是自动强一致

主库提交 binlog→副库接收 relay log→回放事务→从库可见

主从延迟下，写后立即读从库可能读不到。可按业务选择读主、会话粘滞、位点等待或接受最终一致。

易错点与工程边界

  • 索引选择性高不代表一定优先，联合索引顺序还要看等值、范围、排序、覆盖和查询频率。
  • 查询使用了索引也可能很慢，例如扫描索引大范围、回表很多、随机 I/O 或锁等待。
  • RR 不能神奇消除所有业务幻读，先区分快照读、当前读和业务写冲突。
  • 大分页的 OFFSET 会扫描并丢弃大量记录，可用稳定排序键做 seek 分页。
  • 分库分表会引入路由、跨分片查询、全局唯一 ID、扩容和分布式事务成本，应先证明单库瓶颈。

直接更新缓存容易遗漏不同查询维度，并发写也可能让旧值覆盖新值。先更新数据库再删除缓存通常让数据库成为事实源，但删除失败、并发读回填旧值和主从延迟仍会造成短暂不一致。可按业务容忍度增加重试队列、订阅 binlog、版本号或延迟双删，但没有零成本强一致。

TIME_WAIT 和 CLOSE_WAIT 分别说明什么

TIME_WAIT 常出现在主动关闭方，用于处理迟到报文并确保最终 ACK 可重传，大量出现要结合短连接、端口范围和连接复用判断，不应直接删除。CLOSE_WAIT 表示对端已关闭而本端应用尚未 close，大量长期存在通常要检查代码资源释放或阻塞路径。

超时

限制等待时间并释放资源，是所有远程调用必须显式设置的失败边界。

重试

只对瞬时错误和幂等操作，在剩余预算内退避重试，避免多层放大。

成熟客户端通常保留本地缓存的实例列表，让控制面短暂故障不影响数据面已有调用。但缓存可能过期，已下线实例仍被访问，因此还需要请求超时、被动失败摘除和恢复探测。注册中心只负责“去哪调用”，不替代调用可靠性治理。

告警应该指向行动

容量

从流量、延迟和资源估算

平均 QPS = 日请求量 / 86400 峰值 QPS = 平均 QPS × 峰值系数 并发量 ≈ 吞吐 × 平均响应时间 所需实例 ≈ 峰值 QPS / 单实例安全 QPS × 冗余系数

单实例安全 QPS 来自压测拐点

滚动发布

逐批替换实例，资源需求低。新旧版本共存，接口与数据结构需向前向后兼容。

蓝绿发布

金丝雀发布

RPO 与 RTO 是业务选择

RPO最多可接受丢失多少时间范围的数据
故障发生检测、决策、切换、验证

易错点与工程边界

  • 平均延迟会掩盖长尾，面向 SLA 必须看分位数、错误和超时分布。
  • 日志不是越多越好，敏感数据泄露、高基数与磁盘写放大会反过来制造事故。
  • 自动扩容存在检测和启动滞后，不能替代限流、预热和基础冗余。
  • 数据库 schema 变更要采用 expand、migrate、contract 等兼容阶段，应用回滚不一定能回滚数据。
  • 复盘要分析系统和流程促成因素，不以寻找个人责任结束，并为行动项设负责人和期限。

高频模板

二分与滑动窗口

左边界二分

static int lowerBound(int[] a, int target) {
    int left = 0, right = a.length;
    while (left < right) {
        int mid = left + (right - left) / 2;
        if (a[mid] < target) {
            left = mid + 1;
        } else {
            right = mid;
        }
    }
    return left;
}

维护区间 [left, right)，循环结束时 left 是首个不小于 target 的位置。

无重复最长子串

static int longestUnique(String s) {
    Map<Character, Integer> last = new HashMap<>();
    int left = 0, answer = 0;
    for (int right = 0; right < s.length(); right++) {
        char ch = s.charAt(right);
        if (last.containsKey(ch)) {
            left = Math.max(left, last.get(ch) + 1);
        }
        last.put(ch, right);
        answer = Math.max(answer, right - left + 1);
    }
    return answer;
}

窗口内保持字符不重复，left 只能向右，整体 O(n)。

故事二

容器 OOM 排障

夜间容器重启→确认 OOM 与进程→GC 趋势→对象 / native 内存→日志 buffer 增长→验证组件策略→修复与监控

面试版主述

信用卡前置系统出现夜间容器重启。排查时先确认容器退出原因和具体进程，再结合 GC 趋势判断内存回收是否有效，通过对象分布或 Heap Dump 缩小持有者范围，并把时间线与日志文件、发送 buffer 增长对齐，最终定位到日志发送确认策略导致消费或确认速度跟不上。修复后继续观察重启、内存水位、GC 和日志积压，并补充 OOM 自动 Dump 与趋势告警。

必须纠正的表达

  • jstat 看到 Full GC 只能说明高内存压力，不能单独证明内存泄漏。
  • jmap -heap 不能直接证明某个大对象为何存活，需要引用链证据。
  • “无需确认也不会丢日志”是过度承诺，要说明缓冲、重试、丢失窗口和审计日志通道。
  • 先核实是业务 JVM、日志 sidecar 还是宿主进程 OOM，命令链必须与进程类型一致。
