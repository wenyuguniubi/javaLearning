闭卷追问

为什么 HashMap 容量通常是 2 的幂？

数组下标可以用位运算代替取模；扩容翻倍后，元素要么留在原位置，要么移动旧容量的偏移量。前提是哈希分布经过扰动，容量为 2 的幂才能让低位掩码覆盖均匀。

ArrayList 扩容会发生什么？什么时候不用它？

空间不足时创建更大数组并复制元素，扩容本身是 O(n)。频繁头部插入、删除或需要稳定并发写时不合适。LinkedList 也不自动更优，因为节点分配、缓存局部性和定位成本可能更差。

String 为什么不可变？

不可变让字符串常量池、哈希缓存、类加载与安全边界更可靠，也天然便于线程共享。不可变不是 final 引用本身，而是对象对外不可观察到状态改变。

Java 21 值得准备哪些特性？

重点准备虚拟线程、记录模式、switch 模式匹配和有序集合。虚拟线程适合大量阻塞型并发任务，不会让 CPU 密集任务自动变快，也不应该按传统线程池思路池化虚拟线程。

闭卷追问

什么时候对象进入老年代？

取决于收集器与配置。常见原因包括多次 Young GC 后达到年龄阈值、动态年龄判断、晋升担保，以及某些收集器对大对象的特殊处理。不要把固定 15 岁当作所有场景的唯一答案。

如何证明是内存泄漏而不是正常缓存？

看稳定负载下 GC 后基线是否持续抬升，对比多次类直方图的实例增量，抓取 Heap Dump，用支配树和 GC Root 引用链找到保留者，再结合业务生命周期判断对象是否本应释放。

为什么 jmap -heap 不能直接证明大对象无法清空？

它主要展示堆配置和整体使用情况，不提供完整对象保留关系。定位对象类型可用类直方图，证明保留原因通常需要 Heap Dump、支配树和引用链。

虚拟线程改变了什么？

它降低了线程创建与阻塞等待成本，使同步阻塞风格更容易支撑高并发 IO。它不增加 CPU 核心，不消除数据库连接等外部资源上限，也要求关注 ThreadLocal 使用和特定阻塞场景。

闭卷追问

volatile 为什么不能保证 i++ 的原子性？

i++ 包含读取、加一和写回多个步骤。多个线程可能读取相同旧值并覆盖写回。volatile 让读写可见，但没有把这组步骤变成不可分割操作。

AQS 的 state 和队列分别做什么？

state 表示同步状态，具体含义由子类定义。竞争失败的线程进入基于节点的同步队列，前驱状态和 park/unpark 协作完成阻塞与唤醒。Condition 还有独立条件队列，signal 后节点转入同步队列重新竞争。

CallerRunsPolicy 为什么能形成背压？

线程池饱和时由提交任务的线程执行，提交者被业务执行占用，提交速度自然下降。但如果提交线程是关键 IO 线程，可能扩大延迟和故障，因此必须结合调用链判断。

如何设计一个不会拖垮下游的并行查询？

先画依赖图，只并行无依赖查询；设置独立有界线程池或并发信号量；总超时与子任务超时协同；限制每请求扇出；明确部分失败策略；监控线程池、连接池和下游 P99。

高频事务失效场景

同类内部调用为什么常导致 @Transactional 失效？

this 调用直接进入目标对象方法，没有经过 Spring 代理，事务拦截器无法工作。可拆分 Bean、从代理调用或使用明确的编程式事务，但应优先重新审视事务边界。

异常被 catch 后为什么可能不回滚？

事务拦截器看到方法正常返回，就按正常路径提交。应按业务语义重新抛出异常或显式标记 rollback-only，同时注意默认回滚规则通常针对 RuntimeException 和 Error。

一个事务方法里启动异步任务会怎样？

常规事务上下文绑定当前线程，异步线程不会自动加入原事务。还可能出现主事务未提交而异步线程读取不到数据。应通过事务后事件、消息或明确的独立事务设计边界。

REQUIRES_NEW 的代价是什么？

它挂起外层事务并创建独立事务，需要额外数据库连接，内外事务锁叠加时可能增加连接池压力和死锁风险。不能把它当作通用的异常隔离开关。

闭卷追问

为什么 B+ 树适合数据库索引？

非叶子节点主要保存键与指针，单页容纳更多分支，树高更低；叶子有序且相连，兼顾等值和范围扫描；页结构适配磁盘与缓存的块式 IO。

RC 与 RR 的 MVCC 核心区别是什么？

普通一致性读中，RC 通常每条语句创建新的 Read View，RR 通常在事务首次一致性读时建立并复用。锁定读和写操作读取当前版本，不能用同一套快照结论概括。

覆盖索引为什么可能更快？

查询所需列可直接从二级索引叶子获得，减少回聚簇索引取整行的随机访问。但索引越宽，写放大、空间与缓存压力越大，需要按查询收益权衡。

发生死锁后应用应该做什么？

数据库会选择牺牲事务回滚，应用需要识别可重试错误并重试完整事务，带有限次数和退避。同时通过统一加锁顺序、缩短事务、合适索引和减少锁范围降低概率。

RDB 便于快照与快速恢复，AOF 记录写命令并可重写。可靠性要结合 fsync 策略、主从复制和备份恢复演练。

穿透

击穿

热点键失效。互斥重建、逻辑过期、提前刷新，避免大量请求同时回源。

雪崩

闭卷追问

先更新 DB 再删缓存，仍可能不一致吗？

可能。删除失败会留下旧值，并发读写也可能形成短暂竞态。应根据一致性要求使用删除重试、变更日志、消息补偿、版本号或直接放弃缓存。不存在脱离业务要求的绝对正确顺序。

Redis 单线程为什么仍然快？

核心命令大多在内存完成，数据结构高效，事件循环减少传统共享数据锁竞争，并通过 IO 多路复用处理连接。现代 Redis 还可用线程处理部分网络 IO，不能简单说整个 Redis 永远只有一个线程。

如何发现并治理热 Key？

结合代理或客户端统计、采样、慢日志、带宽和实例 CPU 定位。治理可以用本地缓存、键拆分、请求合并、读副本和限流，同时防止一致性与失效风暴。

缓存应该保存 null 吗？

对合法的不存在结果可短 TTL 缓存空值，降低穿透。但要区分查询失败与确实不存在，并考虑数据随后创建时的失效或较短不一致窗口。

闭卷追问

如何保证消息不丢？

先定义允许的语义。生产端用本地事务与 Outbox 或可靠发送、合适的 acks 和重试；Broker 配置足够副本与同步副本要求；消费端处理成功后再提交位点；全链路有监控、补偿和对账。任何单一参数都不是完整答案。

为什么手动提交 offset 仍可能重复？

业务处理成功后、提交位点前进程崩溃，重启后会再次消费。若先提交再处理则可能丢业务。因此消费者必须幂等，并让位点提交与业务状态的关系可恢复。

Kafka 幂等生产者解决了什么，没解决什么？

它防止同一生产会话中因重试造成的分区内重复写，并维护顺序约束。它不自动消除应用主动重复发送，也不让消费者业务自动幂等。跨会话恢复需要事务标识等额外机制。

如何扩容消费者仍不提升吞吐？

消费者并行度受分区数量上限约束，或者瓶颈在数据库、外部接口、锁、单条消息计算和网络。盲目扩容还可能加剧再均衡和下游压力。

闭卷追问

TIME_WAIT 为什么存在？

让最后 ACK 丢失时可以重发，并让旧连接中的延迟报文在网络中消失，避免污染相同四元组的新连接。大量 TIME_WAIT 要先看连接复用、短连接模式和谁主动关闭，不能直接调内核参数。

连接超时、读超时、请求总超时有什么区别？

连接超时限制建连阶段，读超时限制等待数据的阶段，总超时限制完整调用预算。重试必须服从总预算，并给下游保留取消和资源释放机会。

Netty EventLoop 被阻塞会怎样？

同一 EventLoop 上的多个 Channel 事件不能及时处理，延迟扩大、心跳超时、连接堆积。应定位慢 Handler，将阻塞业务提交到受控业务线程池，并监控队列与拒绝。

服务突然大量 502 如何排查？

先确认 502 由哪一层产生，再看网关上游连接错误、实例健康、线程池与连接池、GC、依赖超时、部署变更和网络指标。用请求 ID 或 tracing 对齐各层证据。

闭卷追问

如何实现支付接口幂等？

以商户订单号或请求号作为业务唯一键，数据库唯一约束兜底；状态机只允许合法迁移；重复请求返回已存在结果；外部支付调用也要传幂等标识；超时后通过查询与对账确认最终状态。

熔断和限流有什么不同？

限流保护容量，拒绝超过预算的流量。熔断根据依赖失败或慢调用状态暂时停止请求，防止持续拖累。两者常组合，但触发信号和目标不同。

配置中心故障时服务应该怎样？

保留最近一次有效配置并本地持久化，变更有版本与校验，拉取失败不覆盖旧值，核心配置支持静态默认值，监控长时间不一致，并避免配置中心恢复时所有实例同时拉取。

灰度发布如何降低风险？

先定义指标与自动回滚阈值，按实例、用户或流量逐步放量，保证新旧版本协议和数据兼容，观察错误率、延迟和业务指标，发生异常快速止损并保留可追溯版本。

编码追问

写完算法后如何自测？

覆盖题目样例、空或最小输入、全相同、严格有序或逆序、重复值、边界值和会触发核心分支的构造用例。先手工走状态，再运行。

为什么比较器不要直接 return a - b？

整数相减可能溢出导致比较结果错误，破坏排序契约。应使用 Integer.compare(a, b) 或按 long 比较。

LRU 的 O(1) 设计是什么？

哈希表 O(1) 定位节点，双向链表 O(1) 移动与淘汰。get 和 put 都要把命中节点移到最近使用端，容量满时删除最久未使用节点并同步移除 Map。

我有 3 年 Java 后端经验，主要参与信用卡分布式核心系统和信用卡前置系统。在信用卡核心中，我负责授权相关模块，参与交易链路性能优化，通过梳理查询依赖、并行执行无依赖查询、缓存稳定参数数据和治理慢 SQL，使快捷 8583 交易稳定在约 100ms，其他相关接口保持在 200ms 以内。在信用卡前置系统中，我参与过一次夜间容器 OOM 排障，通过进程、GC、对象和日志增长证据定位到日志发送 buffer 堆积，并补充了 Heap Dump 和内存趋势告警。除此之外，我还做过生产流水线、代码走查和信创改造。下一步我希望进入更高并发、更复杂业务场景，继续加强系统设计和稳定性治理能力。
